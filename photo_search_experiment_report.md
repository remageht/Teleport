## 1. Архитектура решения

Поиск реализован на базе легковесного перцептивного анализа изображений без привлечения тяжёлых нейросетевых библиотек (ONNX, TFLite не использовались, зависимости `pubspec.yaml` не менялись):

* **Сервис:** [`PhotoSearchService`](file:///c:/dev/radiotrade/lib/services/photo_search_service.dart)
* **Комбинированная сигнатура (`ImageSignature`):**
  1. **dHash (512 бит):** 256 бит градиента по горизонтали ($17 \times 16$) + 256 бит по вертикали ($16 \times 17$). Устойчив к вариациям яркости, контрастности и масштабированию.
  2. **aHash (64 бита):** бинаризация средней яркости $8 \times 8$ для фиксации общего силуэта.
  3. **pHash (64 бита):** двумерное сепарабельное косинусное преобразование (2D DCT) матрицы $32 \times 32$ с отбором низких частот $8 \times 8$ (без DC-компоненты).
  4. **Color Grid ($4 \times 4$):** 48 байт (16 блоков $\times$ RGB) для оценки пространственного распределения цвета.
* **Мульти-ориентационный матчинг:** для фото-запроса вычисляются 4 сигнатуры (повороты на 0°, 90°, 180°, 270°). Позволяет корректно сопоставлять фото независимо от того, как пользователь держал телефон (альбомная/портретная ориентация).
* **Фоновые вычисления:** поиск и декодирование выполняются в отдельном изоляте через `compute()`, исключая зависания интерфейса (UI остаётся отзывчивым).
* **Интерфейс склада:**
  * В поисковой строке [`WarehouseScreen`](file:///c:/dev/radiotrade/lib/features/warehouse/warehouse_screen.dart) добавлена кнопка `IconButton.filledTonal` с иконкой `image_search` («Найти по фото»).
  * Диалог выбора источника (Камера / Галерея).
  * Предупреждение при малом числе фото в базе: `«Мало фото для поиска (в базе N, рекомендуется от 10)»`.
  * Модальная панель Top-5 похожих товаров с миниатюрой запроса, процентом совпадения и переходом в карточку товара [`ProductDetailScreen`](file:///c:/dev/radiotrade/lib/features/warehouse/product_detail_screen.dart) по нажатию.

## 2. Результаты измерений

### 2.1. Точность (Accuracy)

| Сценарий тестирования | Top-1 | Top-5 | Примечание |
| :--- | :---: | :---: | :--- |
| **Синтетические эталоны (Unit-тесты)** | 100% | 100% | Идентичные фото дают 100% схожесть; поворот на 90° даёт >80% |
| **Кроп (10%) и сжатие** | 100% | 100% | Сигнатура устойчива к незначительному кадрированию |
| **Реальные фото с камеры смартфона (12 Мп)** | **28.6%** (2/7) | **42.9%** (3/7) | **Ниже целевого порога 50%** |

#### Причины просадки точности на реальных фото:
1. **Специфика каталога радиодеталей:** большинство радиоэлектронных компонентов (микросхемы в корпусах DIP/SOIC, транзисторы TO-220, резисторы, конденсаторы) визуально выглядят практически идентично (чёрный прямоугольник с металлическими выводами).
2. **Отсечение высокочастотной информации:** перцептивный хэш редуцирует картинку до матрицы $8 \times 8$ или $16 \times 16$. Мелкий текст маркировки (например, разница между `NE555` и `LM358`) полностью теряется.
3. **Фоновые помехи:** стол, пальцы руки, тень от телефона и наклон поверхности вносят до 30–40% различий в геометрию и цвет.

### 2.2. Скорость (Performance)

| Количество фото кандидатов в базе | Время выполнения поиска | Оценка UX |
| :---: | :---: | :--- |
| **10 фото** | ~2.45 сек | Приемлемо (с диалогом загрузки) |
| **50 фото** | ~12.2 сек | Неудовлетворительно |
| **100 фото** | ~24.5 сек | Неприемлемо (таймаут пользователя) |

* **Сравнение хэшей:** <0.1 мс на всю базу (битовые операции `popcount64` работают мгновенно).
* **Узкое место:** Декодирование оригинальных JPEG-файлов с диска средствами `image.decodeImage()` в чистом Dart занимает **~245 мс на 1 фото**. Без предрасчитанного кэша хэшей время растёт строго линейно с каждым товаром, имеющим фото.

## 4. Итоговое заключение: Годен или нет для продакшна?

### **Вердикт: НЕ ГОДЕН в текущем виде для основного каталога радиотоваров.**

### Аргументация:
1. **Недостаточная точность для радиодеталей (42.9% Top-5 вместо требуемых $\ge 50\%$):**  
   Перцептивный хэшинг (dHash/pHash) проектировался для поиска дубликатов фотографий и картинок с выраженным макро-рисунком (одежда, обложки книг, логотипы, мебель). Для радиотоваров критична **текстовая маркировка** на корпусе, которую pHash физически не видит.
2. **Проблема масштабирования скорости без изменения БД:**  
   Поиск «на лету» без сохранения сигнатур в БД делает поиск неприменимым уже при 30–50 товарах с фото (задержка >7–12 сек).

### Что требуется для перевода в рабочий продакшн:
1. **Кэш сигнатур в SQLite:** добавить таблицу `product_photo_signatures` (или колонку `photo_hash`), чтобы хэш вычислялся один раз при съёмке товара. Поиск по 1000 товарам тогда займёт **менее 20 мс**.
2. **Гибридный поиск (OCR + Visual):** для радиодеталей наиболее эффективен поиск по текстовой маркировке (через уже внедрённый в проект ML Kit OCR с вырезанием центральной зоны корпуса) в комбинации с перцептивным хэшем только для проверки типа корпуса (DIP, SMD, TO-220, катушка).
